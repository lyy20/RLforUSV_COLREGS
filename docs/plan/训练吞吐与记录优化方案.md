# 训练吞吐与记录优化方案（2026-10-09 讨论稿）

> 目标：找出**真正拖慢训练的部分**，用实测数据定方案，而不是凭直觉。

## 一、硬件清册（本机实测）

| 项 | 实测值 |
| --- | --- |
| CPU | **Intel i7-12700KF**（12 物理核 = 8P+4E，**20 逻辑线程**，3.6 GHz） |
| 内存 | 31.8 GB（训练时可用约 18 GB） |
| GPU | RTX 4070 **12 GB**（训练占用约 2.3 GB；**三进程并发会 CUDA 报错**） |
| 磁盘 | 单 run 1100 回合：TB 日志 2.6 MB、**checkpoint 1251.8 MB（35 文件）**、评估产物 65 MB |

## 二、实测吞吐（每档 60 回合，单进程串行、无残留进程）

| `parallel_envs` | 60 回合耗时 | 吞吐（回合/s） | 结论 |
| --- | --- | --- | --- |
| **16** | 115 s | 0.522 | 基准 |
| **36**（当前配置） | 108 s | **0.556** | 与 16 档**基本持平（+6%，在噪声内）** |

### ⚠️ 先纠正我自己一个错误结论

首轮 benchmark（各档 75 s 采样）显示 16 档比 36 档快 27%，我据此准备建议「降到 16 线程」。
**复测发现首轮测量被残留进程污染**（前一轮进程未退出、与新进程争 CPU），该结论**作废**。
干净复测结论：**`parallel_envs` 16→36 对吞吐几乎无影响**。

⇒ **CPU 并行度不是瓶颈**（20 逻辑线程虽被 36 进程超订，但 env 进程大部分时间在等 GPU/Python 开销），
**真正的成本在每步计算量与 I/O 上**。

## 三、记录冗余分析（实测 122 个标量）

| 组 | 数量 | 占比 | 处置建议 |
| --- | --- | --- | --- |
| **`performance/`（性能剖析）** | **72** | **59%** | **全关**（`PROFILE_TRAINING=False`）——既省 I/O 又省计时开销 |
| `agent0/` | 38 | 31% | 精简到约 14（见下表） |
| `rule_buffer/` | 10 | 8% | 保留 7（去掉累积量的重复项） |
| `landmark0/` | 2 | 2% | 保留 1 |

### 建议保留清单（122 → 约 25）

| 类别 | 保留标量 |
| --- | --- |
| 学习健康（4） | `mean_episode_rewards`、`agent_collision_episode`、`agent_outofworld_episode`、`done_reason_success_episode` |
| 任务进度（3） | `target_distance_mean_episode`、`capture_distance_mean_episode`、`min_clearance_mean_episode` |
| **规则学习（核心 7）** | `rule_filter_active_rate_episode`、`action_chain_raw_to_constrained_mean`、`action_chain_constrained_to_rule_mean`、`action_chain_rule_to_smoothed_mean`、`rule_buffer/size`、`rule_buffer/fill_ratio`、`rule_buffer/teacher_query_rate` |
| 规则质量（3） | `teacher_confidence_mean`、`teacher_valid_rate`、`unknown_type_rate` |
| 控制代价（2） | `rudder_angle_abs_deg_mean_episode`、`yaw_rate_abs_deg_s_mean_episode` |
| 奖励分量（4） | `reward_component_progress`、`reward_component_safety`、`reward_component_success`、`reward_component_intervention` |
| **建议新增（4）** | `actor_loss`、`critic_loss`、`alpha`/`entropy`、`rule_imitation_loss`（当前**完全没有**损失类标量，训练健康无法判断） |

被删的都是**重叠项**：11 个 reward 分量（保留 4）、4 个 done_reason（保留 1）、`rule_buffer/agent0_size` 与 `size` 重复、`inserted_total/sampled_total` 是累积量（可由 size 推导）。

## 四、存储优化

| 项 | 现状 | 建议 | 收益 |
| --- | --- | --- | --- |
| `POLICY_SAVE_INTERVAL` | 200（500k 回合 ⇒ **2500 个 × 1 MB ≈ 2.5 GB**） | **5000**（100 个 ≈ 100 MB） | −96% 存储与 I/O |
| checkpoint 命名 | `episode_last.pt` + `episode_best.pt` + 0 KB 标记 | 保留 last/best，清理旧空标记 | 目录清爽 |
| TB 日志 | 2.6 MB/1100 回合 → 500k 回合 ≈ 1.2 GB | 配合标量精简，预计 **≤0.3 GB** | −75% |
| 评估 GIF/CSV | 65 MB/次评估 | 训练期不生成；只在最终评估生成 | 省时省盘 |

## 五、真正的成本在哪（需下一步实测）

| 旋钮 | 现值 | 说明 | 建议 |
| --- | --- | --- | --- |
| `UPDATE_TIMES` | **16** | **每步 16 次梯度更新**——极可能是最大成本项 | 实测 4 / 8 / 16 的吞吐与学习曲线 |
| `BATCH_SIZE` | 256 | 每次更新批量 | 可测 128 |
| `RULE_ACTOR_BATCH_SIZE` | 16 | 规则模仿额外批量 | 可测 8 |
| `RULE_BUFFER_SIZE` | 100000 | 规则经验池 | 可降到 30000 |
| `PROFILE_TRAINING` | **True** | 72 个性能标量 + 计时开销 | **False** |

## 六、算力预算（按实测 0.55 回合/s）

| 方案 | 计算 | 墙钟 |
| --- | --- | --- |
| 单 run **500k 回合** | 500000 / 0.55 s | **≈ 252 小时 ≈ 10.5 天** |
| 3 seeds × 单臂 | 3 × 10.5 天 | **≈ 31.5 天** |
| 3 seeds × 单臂（2 进程并发，已证 GPU 可承受 2 个） | /2 | **≈ 16 天** |
| 2 臂 × 3 seeds（filter / filter+模仿） | 6 × 10.5 天 / 2 | **≈ 31 天** |

**结论：动手前必须先确认「500k 回合是否真的够收敛」**，否则 31 天可能全部作废。

## 七、我建议的验证顺序（低成本 → 高成本）

1. **先跑 30k 回合的诊断曲线**（约 15 小时/run）：看 `rule_filter_active_rate`、`rule_buffer/fill_ratio`、`mean_episode_rewards` 是否进入平台期；
2. 若平台期在 100k 前出现 ⇒ 用 100k 做多 seed 对比（成本降 5 倍）；
3. 再做 `UPDATE_TIMES` 4/8/16 的吞吐 × 学习曲线小规模对照（各 30k 回合，约 15 小时/档）；
4. 最后才开 500k 的正式实验。
